# 용어집

문서에 반복해서 나오는 작업 용어를 한 줄씩 풀었습니다.
제가 쓰는 지식 저장소의 공통 용어 사전을 바탕으로 했습니다. 그 사전을 어떻게 관리하는지는 [03 지식 루프 §6](03-knowledge-loop.md#6-용어-사전--은어도-검사한다)에 있습니다.

## 하네스 구조

- **하네스** — 에이전트가 무엇을 먼저 읽고, 누구에게 일을 넘기고, 어디서 멈출지를 정한 장치 전체. 규칙 문서·서브에이전트·커맨드·훅·CI를 묶어 부릅니다.
- **CLAUDE.md** — 에이전트가 세션을 시작할 때 자동으로 읽는 규칙 문서. 전역·저장소·모듈 세 층으로 나눴습니다.
- **서브에이전트** — 메인 에이전트가 일을 넘기는 별도 에이전트. 맥락을 따로 가지므로 구현자의 생각에 덜 끌려갑니다. 개발 파이프라인에서는 planner·tester·reviewer 셋을 씁니다(화면 디자인 구현 전용 에이전트가 하나 더 있습니다).
- **planner · tester · reviewer** — 각각 설계만 하는 역할, 구현자의 설명 없이 명세에서 테스트를 짜는 역할, 편집 도구 없이 diff를 비판만 하는 역할.
- **커맨드** — `/feature`·`/bugfix` 처럼 작업 순서를 고정한 슬래시 명령.
- **워크트리** — 같은 저장소를 세션마다 따로 꺼내 쓰는 git 작업 디렉터리. 코드는 나뉘지만 DB·포트·빌드 캐시는 나뉘지 않습니다.
- **통합 브랜치** — 작업 브랜치가 모이는 공용 브랜치(dev·main 등).
- **아키텍처 불변식** — 오래 지켜져야 하는 구조 규칙. 저장소마다 `ARCHITECTURE.md` 에 적고, 기계가 잡는 규칙과 아무도 잡지 않는 규칙을 나눠 둡니다.
- **SoT (Source of Truth)** — 진행과 완료를 판단하는 기준 문서. 여기서는 요구사항 정의서·WBS·설계 문서 묶음입니다.

## 검증

- **초록 · 빨강** — 테스트나 CI의 통과·실패 표시를 부르는 말. 작업 노트에 자주 나옵니다.
- **거짓 통과(거짓 초록)** — 통과로 보이지만 실제로는 아무것도 검증하지 않은 상태. 캐시에서 복원된 테스트, 대상이 0개인 검사 등이 있습니다. 반대는 정상인데 실패로 나오는 경우입니다.
- **FROM-CACHE · UP-TO-DATE** — Gradle이 태스크를 실행하지 않고 이전 결과를 쓸 때 붙이는 표시. 이 표시가 붙은 테스트는 이번에 돈 것이 아닙니다.
- **비공허성** — 검사 대상이 0건이라 저절로 통과하는 일이 없도록, 대상이 실제로 있었음을 같은 테스트 안에서 확인하는 것.
- **실측** — 문서나 기억에 적힌 전제를 믿지 않고 명령·조회로 직접 재서 확정하는 것.
- **프로브** — 원인이나 동작을 확인하려고 잠깐 돌려 보는 10줄 안팎의 임시 코드나 요청.
- **대역** — 에뮬레이터·in-memory DB·fake처럼 실물을 흉내 내는 대체물. 받아 주는 동작은 흉내 내도 실물이 거부하는 규칙은 자주 빠집니다.
- **라이브 검증** — 단위·통합 테스트가 아니라 실제로 띄운 서비스와 화면으로 끝까지 확인하는 것.
- **전수** — 표본이 아니라 모든 대상을 빠짐없이 세거나 돌려 보는 것.

## 실패의 모양

- **조용한 실패** — 실패나 부재가 오류 없이 정상처럼 보이는 결함. 오류 없이 0건이 나오는 조회가 대표적입니다.
- **드리프트(표류)** — 문서·설정·기억이 실제로 도는 코드나 자원과 어긋나 낡아 가는 것.
- **오탐** — 정상인데 문제로 판정하는 것. 규칙을 기계 검사로 옮길 수 있는지는 오탐률로 정합니다.
- **표면** — 같은 사실이 드러나는 접점. 화면·로그·감사 기록·API 응답·자동 로드 문서 등입니다.

## 막는 장치

- **게이트** — 통과하지 못하면 진행을 막는 지점. 저장 거부, CI 검사, 병합 전 확인 등입니다.
- **PreToolUse 훅** — 에이전트가 도구(셸 명령·파일 편집)를 쓰기 직전에 끼어드는 훅. 병합 전 리뷰 확인, 착수 전 위키 검색 확인을 여기에 걸었습니다.
- **fail-open** — 검사 장치가 오류를 내면 막지 않고 통과시키는 설계. 모든 세션에 걸리는 훅이라, 고장이 작업 전체를 세우지 않게 했습니다. 통과 사유는 로그로 남겨 셉니다.
- **잠금 (테스트)** — 규칙이나 동작을 테스트로 고정해, 어기면 CI가 막게 하는 것. DB 행 잠금과는 다른 뜻입니다.
- **래칫** — 기존 위반은 목록에 묶어 두고 새 위반만 막는 검사. 고치면 목록도 줄여야 통과합니다.
- **빌드 슬롯** — 머신 전체에서 동시에 도는 빌드 수를 제한하는 장치. 상한을 넘으면 기다리거나 원격 VM으로 보냅니다.
- **MR 파이프라인** — 병합 요청마다 도는 CI. 변경 범위 판정과 검증이 매번 돌고, 통합 테스트는 정기 실행이나 수동 실행으로 돕니다.

## 지식 루프

- **작업 노트** — 세션이 끝날 때 남기는 기록. 무엇을 했는지보다 왜 그렇게 정했는지를 중심으로 씁니다.
- **로컬 RAG** — 작업 노트를 로컬에서 임베딩해 두고, 에이전트가 질문과 비슷한 노트를 검색해 근거로 쓰게 하는 구성.
- **MCP** — 에이전트가 외부 도구를 부를 수 있게 하는 표준 프로토콜. 위키 검색(`search_wiki`)을 이 방식으로 붙였습니다.
- **세션 감사** — 에이전트의 세션 기록을 매일 읽어 규칙 위반 후보를 찾는 작업. 판정은 사람이 합니다.
- **승격** — 같은 실수가 두 번 나면 그 교훈을 작업 노트에서 규칙 노트(`30_knowledge`)로 올리는 것.
- **habit · lens · invariant** — 규칙 노트의 세 종류. habit은 에이전트의 작업 습관이라 규칙 문서에 한 줄로 둡니다. lens는 사람이나 모델이 diff를 읽어야 하는 점검 질문입니다. invariant는 테스트·검사로 기계가 막는 규칙입니다.
- **점검 색인** — lens 규칙을 한 줄씩 모은 목록. planner와 reviewer가 매번 전부 훑습니다.
- **`hits`** — 같은 실수가 발생한 횟수. 확인된 것만 세는 하한입니다. 이 문서들에서는 "발생 기록"이라고도 부릅니다.
- **`mechanize`** — 규칙을 기계 검사로 옮길 수 있는지에 대한 판정 기록. 검사 경로, 또는 "불가"·"보류"와 그 이유를 적습니다.
- **`guards`** — 규칙을 실제로 집행하는 검사 파일의 위치. 그 파일이 통합 브랜치에 실제로 있는지를 매일 확인합니다.
- **꼬리형** — 리뷰를 받은 뒤 지적을 반영한 커밋을 다시 리뷰받지 않고 병합하는 모양. 리뷰를 아예 안 한 경우보다 흔했습니다.

## 그 밖

- **슬롭** — AI가 대량으로 만들어 낸, 길고 정돈되지 않은 결과물을 낮춰 부르는 말. [출발점](appendix-a-origin.md)의 강연 제목에서 왔습니다.
- **공유 인프라** — 모든 워크트리와 세션이 함께 쓰는 개발 DB·포트·메시지 큐·전역 설정. 한 세션의 상태가 다른 세션의 검증을 오염시킵니다.
