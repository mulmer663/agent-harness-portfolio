# 05. 배운 것 · 한계 · 지금도 사람이 하는 일

## 배운 것

### 1. 규칙은 발생 횟수로 관리한다
처음에는 실수할 때마다 CLAUDE.md에 한 줄씩 보탰습니다. 문서가 길어지자 넘겨 읽히기 시작했고, 같은 실수가 다시 났습니다.
지금은 이렇게 운영합니다.
- 규칙마다 같은 실수가 발생한 횟수(`hits`)를 셉니다.
- 기계로 내릴 수 있는지 판단한 기록(`mechanize`)을 남깁니다.
- 발생 기록이 많은 규칙부터 게이트로 내립니다.

리뷰 위임 규칙은 발생 기록이 34까지 쌓인 뒤에야 게이트가 됐습니다([사례 4](01-case-studies.md#4-리뷰-없이-통합-브랜치에-병합했다--규칙에서-게이트로)). 돌아보면 더 일찍 내렸어야 했습니다.

### 2. 작성자와 검토자를 분리한다
구현한 에이전트가 테스트까지 짜면 같은 오해가 양쪽에 들어갑니다. tester에게는 명세만, reviewer에게는 읽기 권한만 줬습니다. 리뷰어의 지적은 고쳐지고 끝나지 않습니다. 기록으로 남아 다음 승격의 재료가 됩니다.

### 3. 테스트 통과 표시만으로는 검증이 아니다
실제로는 검증이 되지 않았는데 통과로 보인 경우를 여러 번 겪었습니다.
- 캐시에서 복원된 테스트
- 대상이 0개인 타입 검사
- 필터를 새어 나온 규칙 테스트
- in-memory 대역 위에서만 통과한 쿼리

그래서 보고 형식을 바꿨습니다. "통과"라고 쓰지 않고 어떤 태스크가 실제로 실행됐고, 몇 건이 돌았는지를 씁니다.

### 4. 병렬 세션에서는 공유 자원이 문제였다
에이전트 세션을 여러 개 띄우면 코드는 워크트리로 나뉩니다. 그러나 다음 자원은 나뉘지 않습니다.
- 개발 DB
- 빌드 캐시
- 포트
- git 스테이징 영역
- 메시지 큐 소비자
- 머신 메모리

사례 5개 중 4개가 공유 자원에서 났습니다. 격리하거나, 상한을 두거나, 착수 전에 상태를 실측하는 규칙이 필요했습니다.

### 5. 자동으로 읽히는 문서를 먼저 고친다
위키에 정답이 있어도 CLAUDE.md가 반대로 적혀 있으면 에이전트는 CLAUDE.md를 따릅니다. 작업 노트에만 적어 둔 교훈은 같은 사고를 두 번째에도 막지 못했습니다([사례 3](01-case-studies.md#3-공유-저장소에서-git-add--a-가-다른-세션의-작업을-쓸어-담았다)). 그래서 틀린 서술은 자동 로드 문서부터 고치고, 거기에는 실측한 사실과 그 실측 명령만 적습니다.

### 6. 반대 방향의 과잉 일반화도 오류다
"이건 안전하다"를 막으려고 "이건 전부 위험하다"고 적으면 방향만 반대인 오류를 심습니다([사례 1](01-case-studies.md#1-공유-개발-db에-적용된-마이그레이션이-다른-워크트리의-기동을-깨뜨렸다)).
전제만으로 확정할 수 없는 것은 버리는 컨테이너로 10줄짜리 프로브를 돌려 실측합니다. 다만 프로브는 동작을 잴 뿐, 그 동작이 맞는지는 그 동작을 규정한 사양이 정합니다.

## 한계

- 지표는 휴리스틱입니다. "리뷰 언급"은 커밋 제목의 키워드이고, `hits` 는 사람이 판정한 하한입니다. 게이트 전후의 차이는 관측이지 인과의 증명이 아닙니다.
- 게이트는 실패하면 엽니다. 모든 세션에 걸리는 훅이라 오류가 나면 통과시킵니다. rebase·cherry-pick처럼 게이트가 보지 못하는 반영 경로도 있습니다. 그래서 못 보는 것을 정의 파일 머리말에 나열해 두었습니다.
- 규칙이 늘수록 읽는 비용도 늡니다. 점검 색인은 매 리뷰마다 전수로 훑습니다. 한 줄 150자 상한과 전역 CLAUDE.md 압축으로 버티고 있지만, 규칙 90개는 이미 가볍지 않습니다.
- 로컬 머신이 상한입니다. 전건 테스트는 로컬에서 돌리지 않고 CI에 맡깁니다. 그래서 로컬에서 영향 범위만 돌린 결과와 CI 전건 사이에 시차가 있습니다.
- 한 사람의 환경에 맞춰져 있습니다. macOS 셸, 특정 에디터, 특정 에이전트 도구를 전제로 합니다. 다른 팀이 그대로 가져다 쓸 수 있는 프레임워크는 아닙니다. 옮길 수 있는 것은 구조와 운영 규칙입니다.

## 지금도 사람이 하는 일

| 일 | 이유 |
|---|---|
| 무엇을 만들지, 무엇을 안 만들지 | 고객 요구·영업 일정·우선순위는 에이전트가 볼 수 없는 정보입니다 |
| 계획 승인 · 병합 승인 | 파이프라인의 두 관문은 의도적으로 사람이 쥐고 있습니다 |
| 우회 허용 | 게이트를 환경 변수로 넘기면 그 사실이 사람에게 보고됩니다 |
| 감사 후보가 진짜 위반인지 판정 | 규칙 날짜, 세션 계보, 게이트 시기를 대조해야 합니다. 모호하면 세지 않는다는 판단도 사람이 합니다 |
| 무엇을 위키에 남길지 고르기 | 캡처는 항상 수동입니다. 자동으로 쌓으면 검색 품질이 떨어집니다 |
| 보안·운영 정책 결정 | 키 회전 절차, 자동 조치 기본값, 공개 범위처럼 되돌리기 어려운 결정입니다 |
| 실물 환경 검증 | 대역 위에서 통과했다고 끝이 아니라서 실물로 한 번 흘려 봅니다. 그 대상과 시점을 사람이 정합니다 |
| 고객에게 나가는 산출물 확인 | 정의서·설명서의 최종 문구와 도표는 사람이 봅니다 |

정리하면, 제가 한 일은 에이전트가 같은 실수를 반복하지 않게 하는 장치를 만들고 그 장치가 실제로 동작하는지 확인하는 것이었습니다.
