# 부록 A. 출발점 — "슬롭에는 슬롭으로"

이 하네스를 지금 모양으로 만든 계기는 강연 하나였습니다.
Vaibhav Gupta(BoundaryML, BAML 개발사)의 "Fighting slop with slop"입니다([영상](https://www.youtube.com/watch?v=bKT2wOec_rg), 한국어 자막을 붙여 다시 올린 판). 2026-08에 영상을 보고 강연 내용을 정리한 문서를 따로 읽은 뒤, 제 작업에 하나씩 대조했습니다.

## 1. 강연 전 — 역할 분리만 있던 골격

강연을 보기 전인 2026-06-04에, 제품 저장소와는 별개인 개인 에이전트 설정에 하네스의 첫 골격을 만들었습니다.

- 이미 나와 있는 멀티 에이전트 프레임워크는 들이지 않았습니다. 에이전트 도구가 서브에이전트·훅·스킬을 이미 대부분 제공하고, 위에 한 겹 더 얹으면 업스트림이 바뀔 때 깨지기 때문입니다.
- 대신 역할(서브에이전트) 3개와 커맨드 3개만 직접 정의했습니다.

| 역할 | 하는 일 |
|---|---|
| **planner** | 코드를 고치기 전에 영향받는 파일, 단계별 계획, 테스트 케이스, 위험을 정리합니다. 처음에는 편집 도구가 없었습니다 |
| **tester** | 구현자의 설명을 받지 않고 계획의 테스트 케이스만 받아 테스트를 짜고 돌립니다. 같은 맥락에서 테스트를 짜면 구현의 오해가 테스트에도 그대로 들어가기 때문입니다 |
| **reviewer** | diff를 읽고 정확성 → 누락 → 단순화 → 컨벤션 순으로 지적만 합니다. 편집 도구가 없습니다 |

| 커맨드 | 순서 | 사람이 확인하는 곳 |
|---|---|---|
| `/feature` (기능 추가) | planner 설계 → 메인 에이전트 구현 → tester 테스트 → reviewer 검토 | 계획이 나온 뒤, 검토가 끝난 뒤 |
| `/bugfix` (버그 수정) | 원인 위치 탐색 → 재현 테스트 작성 → 원인 분석·수정 → tester 회귀·인접 케이스 테스트. 재현이 안 되면 첫 단계로 돌아갑니다 | 원인 확인 |
| `/review-mine` (셀프 리뷰) | 현재 변경분을 reviewer에게 넘기고, 지적을 요약하지 않고 그대로 받습니다 | 병합 판단 |

- planner와 reviewer에게서 편집 도구를 뺀 이유는, 본문에 "코드를 고치지 마라"고 적는 것보다 권한에서 빼는 쪽이 확실하기 때문입니다. 다만 셸은 남겨 두었으므로 완전히 막히지는 않습니다.
- 2026-10-01부터 planner는 계획을 파일로 남기고 설계 그림까지 만들도록 바뀌어, 파일 쓰기 권한도 받았습니다. 그 뒤로 planner가 코드를 고치지 않는 것은 지시에 더 기대게 됐습니다. reviewer에게는 지금도 편집 도구가 없습니다.
- 이 셋은 지금도 쓰고 있습니다. 이후 커맨드는 성능 검증 등이 더해져 늘었고, 지금 구성은 [02 하네스](02-harness.md#3-파이프라인--슬래시-커맨드로-고정한-순서)에 있습니다.

이때는 역할을 나눴을 뿐, 무엇을 기계로 막을지는 정하지 않은 상태였습니다. 불변식 문서, 린트 게이트, 실행 트레이스 도구는 모두 강연 뒤에 생겼습니다(날짜는 §3과 §6).

## 2. 강연에서 가져온 틀

제가 정리한 강연의 요지는 이렇습니다.
에이전트가 코드를 쏟아내는 속도를 사람이 한 줄씩 읽어서 따라갈 수는 없습니다. 그러니 리뷰를 기계가 검사할 수 있는 제약으로 바꿔야 합니다.
그 제약으로 다섯 가지를 들었습니다.

1. 글이 기준(SoT)이다 — 코드보다 먼저 요구와 설계를 글로 고정한다
2. 아키텍처 불변식은 최소로 — 규칙 파일이 커지면 모델이 무시하거나 지어낸다
3. CI가 기계로 검증한다 — 사람의 눈 대신 빌드가 깨진다
4. 실행 트레이스를 남긴다 — "안 돼요" 대신 무슨 일이 있었는지를 넘긴다
5. 타입을 강하게 — 타입과 구조 검사가 잡을 수 있는 것은 거기서 잡는다

#### 왜 1인 개발에 더 맞았나

이 주장은 "리뷰어가 모자라다"는 전제에서 출발합니다. 저는 리뷰어가 0명이었습니다. 그래서 강연의 틀이 팀보다 저에게 더 그대로 맞는다고 판단했습니다.
개발자가 아닌 동료들도 다시 봤습니다. 코드 리뷰는 할 수 없어도 이 루프의 양 끝은 맡을 수 있습니다. 앞단에서는 요구와 수용 기준을 쓰고, 뒷단에서는 실행 트레이스를 만들어 줍니다.

## 3. 다섯 가지를 대조한 결과 (2026-08-18)

| 인사이트 | 이미 있던 것 | 빈 곳 | 그날 한 일 |
|---|---|---|---|
| ① 글이 SoT | 요구사항 정의서 → WBS → 설계 문서 | 변경 요청이 정제 없이 들어왔습니다. 과거 커밋 3건을 거꾸로 따라가 보니 셋 다 요청이 "무엇을 원한다"가 아니라 "어떻게 고쳐라"였습니다 | 요청서 양식을 만들었습니다. 수용 기준은 "누가·어디서 무엇을 하면 화면에 무엇이 보인다" 한 줄로 씁니다. DB·로그 같은 화면 밖 내용은 수용 기준이 아니라 작업 완료 조건으로 보냅니다 |
| ② 최소 불변식 | 저장소 CLAUDE.md와 규칙 문서 | 규칙 문서가 커서 넘겨 읽힐 위험이 있었습니다 | 불변식 문서(ARCHITECTURE.md)를 따로 만들었습니다(§5) |
| ③ CI 기계 검증 | 병합 뒤에 도는 CI | CI가 게이트가 아니었습니다. 프런트엔드에는 구조 린트가 없었습니다. 백엔드와 프런트엔드 테스트 job이 동시에 최소 4일 동안 빨간 채로 지나갔는데 아무도 몰랐습니다 | 먼저 빨간 테스트를 고쳤습니다. 이미 실패하는 job에 린트를 얹어 봐야 아무도 보지 않기 때문입니다. 통과시키려고 단언을 약하게 만들지는 않았고, 판단이 필요한 1건은 건너뜀 표시와 사유를 남겨 분리했습니다. 그다음 프런트엔드 모듈 경계 린트를 CI에 넣었습니다 |
| ④ 실행 트레이스 | 요청 상관 ID | 테스트 담당자의 피드백에 상관 ID가 실려 오지 않았습니다. 서버 로그 패턴에도 상관 ID가 찍히지 않고 있었습니다 | 화면의 "피드백 복사" 버튼(현재 화면·사용자·마지막 요청의 상관 ID·시각)과, 상관 ID 하나로 로그·이벤트·변경 이력을 한 번에 뽑는 덤프 스크립트를 만들었습니다. 피드백 버튼은 내부 진단용이라 데모 빌드에서만 켜지고 기본값은 꺼짐입니다 |
| ⑤ 강타입 | 아키텍처 테스트 8개, TS strict | 큰 빈 곳은 없었습니다 | 이후 구조 테스트를 계속 늘렸습니다. 다만 넓게 `catch (Exception)` 으로 삼키는 곳과 타입 없는 맵이 많다는 것을 확인했고, 남은 과제로 기록했습니다 |

계획은 그날 아침에 세웠고, ①~④는 같은 날 구현해 통합 브랜치에 병합했습니다.

## 4. 계획이 실측으로 뒤집힌 곳

배운 것은 계획대로 된 곳보다 계획이 틀렸다고 드러난 곳에서 더 많이 나왔습니다.

#### 상관 ID — 클라이언트가 감사 키를 고르게 될 뻔했습니다
- 계획은 "마지막 응답의 상관 ID를 피드백에 담자"였습니다.
- 조사해 보니 서버는 상관 ID를 응답에 주지 않았습니다. 대신 클라이언트가 보낸 요청 ID를 그대로 감사 키로 채택하고 있었습니다.
- 그대로 쓰면 브라우저가 감사 키를 고르는 셈입니다. 다른 요청의 감사 그룹과 겹치는 값을 첫 요청에 넣어 변경 이력을 섞을 수 있습니다.
- 중복 거절이나 디바운싱으로는 막을 수 없습니다. 문제는 "반복"이 아니라 "선택"이라 첫 쓰기를 막지 못합니다.
- 그래서 받되 채택하지 않도록 바꿨습니다. 감사 키는 서버가 항상 새로 만들고, 클라이언트 값은 로그에 참고용으로만 남깁니다. 테스트 담당자가 들고 다니는 값이 감사 키와 같을 필요는 없습니다.
- 응답 헤더로 감사 키를 돌려주는 안을 처음에는 "인증 실패·시간 초과에는 값이 없다"는 이유로 기각했습니다. 그런데 reviewer가 같은 브랜치의 실측을 들어 그 근거가 자기모순이라고 지적했습니다. 인증 실패는 필터 단계에서 끊겨 어차피 로그에도 아무것도 남지 않았습니다. 그래서 응답 헤더를 더했습니다.
- 실제로 돌려 보니 성공한 조회 요청은 로그를 한 줄도 남기지 않았습니다. 클라이언트 값만으로는 추적할 수 없는 요청이 실재했던 것입니다.

#### 기록이 사실에서 표류해 있었습니다

작업 노트에는 "상관 ID가 찍히는 구조화 로그가 이미 있다"고 적혀 있었습니다. 실제로는 성능 계측 줄 일부에만 찍히고 있었습니다. 이걸 그대로 믿었으면 덤프 스크립트의 로그 절은 늘 0건이었을 것입니다.

#### 요청서 위치

계획은 "요구사항 정의서에 수용 기준 열을 더하자"였습니다. 열어 보니 같은 역할의 열이 이미 있었고 105행 중 59행이 채워져 있었습니다. 게다가 정의서는 요구 1건마다 버전을 올리는 고객 산출물이었습니다. 그래서 요청서를 정의서 앞단의 접수 버퍼로 두고, 정제를 거쳐 새 요구로 판정된 것만 정의서로 올리게 했습니다.

## 5. 불변식 문서를 쓰는 규칙

강연의 경고("규칙 파일이 커지면 무시된다")를 문서 구조로 옮겼습니다.

- 강제되는 규칙과 안 되는 규칙을 절로 나눕니다.
  - A절은 기계가 잡는 규칙입니다. 어기면 빌드가 깨지니 외울 필요가 없고, 어디서 잡는지만 적습니다.
  - B절은 아무도 잡지 않는 규칙이고, 이것이 본론입니다.
  - 둘을 같은 톤으로 나열하면 읽는 쪽이 둘을 똑같이 취급합니다. 고치려던 문제("고개만 끄덕이고 마는 목록")를 축소판으로 다시 만드는 셈입니다.
- 개수·현재 상태·도구 버전은 적지 않습니다.
  - 다른 모델에게 "2~3년 지켜질 규칙만 있는가"라는 관점으로 리뷰를 맡겼습니다.
  - 그 리뷰가 쓰는 시점에 이미 거짓인 문장을 찾았습니다. "전부 잡힌다"고 적은 규칙에 실제로는 대상 2개가 빠져 있었습니다.
  - 문장만 고치지 않고 빠진 2개를 막는 테스트를 더했습니다. 숫자는 문서·설정·CI 세 곳에 중복돼 세 배로 낡고 있었으므로 문서에서 걷어냈습니다.
- B절 규칙을 테스트로 잠그면 A절로 옮깁니다. 그래서 B절은 시간이 갈수록 짧아져야 합니다. 이튿날 B절 일부를 새 구조 테스트로 잠가 12줄을 7줄로 줄였습니다.
- 같은 구조를 나머지 두 제품에도 썼습니다. 세 제품의 불변식 문서가 처음 들어온 날은 IAM 플랫폼 2026-08-18, 유출 계정 탐지 2026-08-28, MFA 제품 2026-09-08입니다. IAM 플랫폼의 문서는 지금까지 29개 커밋에 걸쳐 고쳐졌습니다.

```bash
# 불변식 문서가 처음 들어온 날 (저장소마다)
git -C <저장소> log <ref> --diff-filter=A --format=%ad --date=short -- ARCHITECTURE.md | tail -1
# 그 문서를 고친 커밋 수
git -C <저장소> rev-list --count <ref> -- ARCHITECTURE.md
```

## 6. 그 뒤 — 강연 너머로

강연의 틀은 코드에 대한 기계 검증입니다. 운영해 보니 코드 테스트로는 잡히지 않는 실수가 남았습니다. 에이전트의 작업 습관에서 나는 실수입니다. 리뷰 없이 병합하기, 공유 저장소에서 남의 작업까지 스테이징하기, 캐시에서 복원된 테스트를 "통과"로 보고하기 같은 것들입니다([사례](01-case-studies.md)).

| 날짜 | 한 일 |
|---|---|
| 2026-06-04 | 하네스 골격: 역할 분리와 권한 차단 |
| 2026-08-18 | 강연 대조 → 요청서 양식, 불변식 문서, 프런트엔드 린트 게이트, 트레이스 도구 |
| 2026-08-28 | 병합 전 reviewer 위임을 습관 규칙으로 승격 |
| 2026-09-29 | 세션 기록을 매일 검사하는 감사 도입 |
| 2026-10-21 | 병합 전 리뷰·착수 전 위키 검색을 게이트로 |

그래서 같은 원칙을 에이전트 자신에게도 적용했습니다.
- 세션 기록을 실행 트레이스처럼 읽는 감사를 만들었습니다([03 지식 루프](03-knowledge-loop.md)).
- 두 번 겪은 습관은 규칙으로 올리고, 그 뒤에도 계속 나면 게이트로 내렸습니다([02 하네스](02-harness.md)).

강연은 코드를 기계로 검사하는 이야기였고, 저는 거기에 에이전트의 작업 방식까지 검사하는 장치를 더했습니다. 나머지 문서는 그 내용입니다.
