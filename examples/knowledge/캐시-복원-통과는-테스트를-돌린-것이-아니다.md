## 문제

빌드 캐시를 켠 저장소에서 `./gradlew :모듈:test` 는 입력이 같으면 테스트를 실행하지 않고 전에 통과한 결과를 복원합니다.
그래도 종료 코드는 0이고 `BUILD SUCCESSFUL` 이 찍히며 결과 XML도 생깁니다. 빌드 캐시는 워크트리끼리 공유되므로, 방금 만든 워크트리에서 처음 돌려도 복원될 수 있습니다.

코드 회귀를 확인할 때는 대개 괜찮습니다. 입력이 같으면 결과도 같기 때문입니다. 문제는 태스크 입력이 아닌 것을 검증할 때입니다.

- 환경: Docker 소켓, 환경 변수, 스크립트 자체의 동작
- 측정: 소요 시간, 자원 사용량
- 변이 테스트: 일부러 깨고 되돌린 뒤의 통과
- 입력으로 선언되지 않은 파일: 테스트가 읽는 다른 디렉터리의 fixture

이때 통과는 아무것도 재지 않은 값입니다.

## 알아보는 법

| 표시 | 뜻 |
|---|---|
| `> Task :모듈:test` | 실제로 실행했다 |
| `> Task :모듈:test FROM-CACHE` | 빌드 캐시에서 복원했다. 실행하지 않았다 |
| `> Task :모듈:test UP-TO-DATE` | 출력이 이미 최신이다. 실행하지 않았다 |
| `> Task :모듈:compileJava FROM-CACHE` | 클래스를 복원했다. 입력 밖 설정이 다른 트리의 컴파일 결과일 수 있다 |

소요 시간이 몇 초뿐이거나, 결과 XML의 `timestamp` 가 실행 시각보다 앞서면 의심합니다.
`-q` 나 좁은 `grep` 으로 출력을 거르면 이 표시가 사라집니다.

## 하는 법

- 한 태스크만 다시: `./gradlew :모듈:test --rerun`
- 전부 다시, 캐시 없이: `./gradlew test --rerun-tasks --no-build-cache`. 의존 태스크까지 다시 돌아 느립니다.
- 인자를 받지 못하는 래퍼 스크립트라면 결과 폴더를 지우고 캐시도 끕니다. 둘 중 하나만 하면 여전히 실행되지 않습니다. 결과만 지우면 FROM-CACHE, 캐시만 끄면 UP-TO-DATE입니다.
- 테스트가 읽는 파일은 입력으로 잡히는 자리(클래스패스 자원)에 둡니다.
- 실행한 뒤에는 대조 실행으로 값이 갈리는지 봅니다. 예를 들어 환경 변수를 주면 건너뜀 0건, 빼면 3건으로 갈려야 판정이 됩니다.

## 변종 — `--tests` 필터를 새어 나온 테스트

캐시를 꺼도 같은 통과가 납니다. ArchUnit의 필드형 규칙(`@ArchTest static final ArchRule`)은 Gradle의 `--tests` 필터를 무시하고 돕니다.
그래서 오타가 난 패턴을 줘도 아키텍처 규칙만 돌고 `BUILD SUCCESSFUL` 로 끝납니다. Gradle의 "No tests found"도 무엇이든 하나가 돌면 울리지 않습니다.

- 보고 전에 결과 XML에 고른 클래스가 실제로 있는지 봅니다. 아키텍처 규칙만 있으면 아무것도 고르지 않은 것입니다.
- 막는 방법은 빌드 스크립트에서 `--tests` 패턴마다 실제로 돈 테스트를 세어, 0건이면 실패시키는 것입니다.

## 왜 습관인가

캐시 재사용은 결함이 아니라 빌드 도구의 정상 동작이라 CI나 린트가 막을 수 없습니다. 이번 실행이 입력 밖의 것을 재려는지는 실행하는 쪽만 압니다.
